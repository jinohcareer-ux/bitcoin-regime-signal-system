# BTC Regime Signal | 비트코인 시장 국면 분석

**Jinoh Lee (이진오) · Python 데이터 분석 포트폴리오**

Binance BTCUSDT 시간봉을 뉴욕시간 기준 일봉으로 변환하고, 이동평균으로 시장 국면을 분류하는 연구용 프로젝트입니다. 과거 데이터를 분석하는 백테스트와 매일 신호를 계산해 Mac 알림으로 전달하는 스크립트로 구성됩니다.

현재 단계는 **연구·알림 프로토타입**입니다. 거래소 주문을 실행하지 않으며, 검증된 초과수익이나 청산 방지를 보장하는 시스템이 아닙니다.

## 1. 문제 정의와 연구 배경

처음 질문은 “특정 시간에 비트코인을 사고팔면 반복 가능한 패턴이 있을까?”였습니다. 이전 분석에서는 매수시간 24개 × 매도시간 24개 = 576개 조합으로 탐색 범위를 넓혔습니다. 레버리지 3개와 손절 설정 10개를 결합하면 설계상 17,280개 조합입니다.

이후 “시장 상태에 따라 노출을 조절하는 것이 유용할까?”로 질문을 확장했고, 이동평균 기반 레짐 모델과 일일 알림을 구현했습니다.

**근거 범위:** 시간대 전수조사는 이전 대화의 연구 기록입니다. 현재 배포 파일에는 전수조사 코드·입력 스냅샷·결과 행렬이 없습니다. 따라서 해당 전수조사를 이 저장소에서 재현할 수 있다고 주장하지 않습니다. 동일 시각 진입·청산 조합의 보유기간 정의도 원 실험에서 확인해야 합니다.

## 3. 데이터와 시각

- 종목: BTCUSDT 현물 가격 데이터. 1.5배 노출은 시뮬레이션 가정입니다.
- API: `https://data-api.binance.vision/api/v3/klines`
- 백테스트 요청 시작일: `2017-08-17`; 종료 시각: 실행 시점. 고정 데이터셋이 아닙니다.
- 신호 스크립트: 최근 260일 요청, 진행 중인 뉴욕 일봉 제외.
- 일봉 기준: `America/New_York`. 뉴욕 자정은 고정 UTC 시각이 아닙니다.
- 첫 유효 신호: 결측 없는 일봉 220개째부터 `SMA200.shift(20)` 계산 가능. 실제 거래는 그 신호를 사용하는 다음 날짜부터입니다.

현재 `hour_count >= 23`은 23·24·25시간인 날을 통과시키지만 **날짜별 기대 시간봉 수를 정확히 검사하지는 않습니다.** 평소 24시간인 날에 1개 봉이 빠져도 통과할 수 있습니다. 일봉이 누락되면 20행 전과 20달력일 전도 달라집니다.

## 4. 시장 국면 규칙

각 행의 조건을 모두 충족해야 합니다. 지표가 준비되지 않은 초기 구간은 백테스트 거래에서 제외합니다.

| 국면 | 조건 | 목표 노출 |
|---|---|---:|
| Strong Bull | 종가 > SMA200, SMA50 > SMA200, SMA200 > 20행 전 SMA200 | 1.5배 |
| Bear | 종가 < SMA200, SMA50 < SMA200, SMA200 < 20행 전 SMA200 | 0배 / 현금 |
| Neutral | 위 두 조건에 해당하지 않는 유효한 경우 | 1.0배 |

1.5배는 자기자본 대비 BTC 가격 노출의 목표값입니다. 알림의 `BUY`는 목표 상태를 나타냅니다. 보유 수량을 읽거나 매일 새 주문을 생성하지 않습니다.

## 5. 백테스트 계산과 제약

초기자본은 1,000 USDT 상당, 수수료 가정은 편도 0.05%입니다. 거래소의 현재 요금이나 사용자 계정 요금을 조회한 값은 아닙니다.

전일 완료 일봉으로 다음 날짜의 목표 노출을 정하는 것이 설계 의도입니다. 수익률은 **뉴욕시간 00:00 시간봉의 시가부터 다음 날짜 00:00 시가까지**로 계산합니다. 원래 의도한 00:01 체결을 1시간봉으로 근사한 것이며 실제 체결가격이 아닙니다.

```text
BTC 수익률 = 다음 시가 / 현재 시가 - 1
총수익률 근사 = 목표 노출 × BTC 수익률
기본 수수료 근사 = |현재 목표 노출 - 이전 목표 노출| × 0.0005
전략 수익률 = 총수익률 근사 - 수수료 근사
자산 = 초기자본 × 누적 곱(1 + 전략 수익률)
```

`DAILY_CLOSE_REOPEN = False`는 목표 노출 차이에만 수수료를 부과하지만, 수익률에는 매일 일정한 목표 레버리지를 곱합니다. **실제 포지션을 그대로 보유하는 계산과 다르며**, 레버리지 유지에 필요한 재조정 비용도 충분히 반영하지 않습니다. 수량·현금·부채를 추적하는 모형이 필요합니다.

`True`에서는 매일 `목표 노출 × 수수료율 × 2`를 부과합니다. 이 역시 진입·청산 시 달라진 거래대금을 따로 추적하지 않는 근사입니다.

### 구현상 확인된 과제

1. **서머타임 정렬:** `Timedelta(days=1)`은 고정 24시간입니다. 전환일에는 다음 자정과 달라져 신호 조인에서 행이 빠질 수 있습니다.
2. **결측:** 날짜별 기대 23·24·25개 봉 검사, 연속성 확인, 누락된 자정 간 다일 수익률 방지가 필요합니다.
3. **낙폭:** 현재 누적 최고값은 초기자본을 포함하지 않아 첫 거래 손실을 올바르게 반영하지 못할 수 있습니다.
4. **평가 기간:** CAGR 분모·종료일은 마지막 행의 진입일을 사용하지만 최종 자산은 그 행의 청산까지 반영합니다.
5. **청산·비용:** 장중 청산, 유지증거금, 펀딩·차입비용, 스프레드·슬리피지, 마지막 포지션 청산비용을 완전하게 구현하지 않았습니다.

이번 수정은 문서와 포트폴리오에 적용했습니다. Python 계산 로직과 사용자의 Mac cron 설정은 변경하지 않았습니다.

## 6. 성과 수치를 공개하지 않는 이유

이전 문서에는 과거 대화의 최종금액·CAGR·MDD가 확정 성과처럼 실려 있었습니다. 그러나 같은 입력·설정으로 재현된 결과 파일은 확보되지 않았고 위 구현 과제도 확인됐습니다. 해당 수익률 표를 이번 공개 문서에서 제외했습니다.

2026년을 별도로 살펴봤더라도 전략 선택·수정에 사용했다면 엄밀한 표본외 검증이 아닙니다. 종료일, 입력 데이터 해시, 설정, 코드 버전, 거래 내역을 고정·저장하고, 수정 후 동일 기간의 단순 보유 기준과 비교해야 합니다.

MDD는 자산 고점 대비 낙폭이고, 청산은 포지션의 증거금 조건과 관련됩니다. 단순한 `1 / 레버리지`의 반대 방향 가격 변동은 비용을 무시한 자본 소진 근사일 뿐 실제 청산가격이 아닙니다.

## 7. 실행과 일일 알림

Python 3.10 이상 권장. 알림은 macOS용입니다.

```bash
python -m pip install -r requirements.txt
python btc_regime_backtest.py
python btc_signal.py
```

연구 출력은 `outputs/trades.csv`, `action_changes.csv`, `strong_bull_2026.csv`, `summary.json`에 저장됩니다.

기존 cron 예시:

```cron
10 0 * * * /opt/anaconda3/bin/python /Users/yourname/Bitcoin/btc_signal.py >> /Users/yourname/Bitcoin/btc_signal.log 2>&1
```

실제 경로를 사용하고, 이미 등록되어 있다면 중복 추가하지 않습니다. cron은 Mac 시스템 시간대를 따릅니다. 뉴욕 00:10 실행을 원하면 Mac 시간대도 뉴욕과 일치해야 합니다.

10월 1일 00:10 실행 시 9월 30일 데이터가 완전하다면 **10월 1일 신호**를 계산합니다. `TOMORROW`는 실행일의 내일이 아니라 마지막 데이터 날짜의 다음 날이므로 `Decision for` 날짜를 기준으로 읽어야 합니다.

Mac이 켜져 있고 깨어 있어야 하며, 인터넷·로그인·알림 권한도 확인해야 합니다. 수동 실행 성공만으로 cron 알림 전달까지 검증되지는 않습니다. 백테스트의 00:00 근사와 00:10 알림 이후 행동은 체결시각도 다릅니다.
